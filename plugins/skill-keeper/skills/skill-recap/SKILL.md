# 任务回顾与改进编排（通用方法论）

每次任务完成后执行此回顾流程。本 skill 是**编排入口**，不自己实现审计/守门逻辑——调用项目定制的守门 skill 完成落盘守门。本版本是跨项目通用方法论，项目定制版应补充本项目的 skill 清单与衔接点（见文末「如何派生项目定制版」）。

## 辅助文件

- `references/decision-trees.md` —— 阶段 3 的改进维度 / 过程反哺 / 四问归类 / 落点矩阵 / 反例 / 去重检查 / 综合考量维度

执行阶段 3 与「综合考量」章节时 Read 该文件，正文不再展开重复。

## 回顾原则

- **轻量快速** — 不超过任务本身时间，只提取有价值信息
- **聚焦改进** — 目标是改进 skill 与文档，不是写流水账
- **具体可操作** — 每条建议明确到文件和修改内容
- **核心业务不忽略** — 涉及项目核心业务链路的新发现哪怕"只影响一处"也必须按「综合考量」评估，默认倾向记录

**值得回顾**：遇到意外问题/弯路、发现现有 skill 遗漏或错误、用了新技巧或模式、任务涉及 skill 覆盖领域但指导不足、核心业务有新发现。

**可以跳过**：typo 修复等琐碎任务、完全按 skill 指导顺利完成、纯调研/阅读任务。跳过时说：「本次任务过程顺利，无需更新 skill。」

## 阶段 1：任务回顾

快速识别三类信息：**成功点**（有效的方法/模式/工具用法、帮了大忙的 skill）、**失败与弯路**（走过的弯路与根因、错误与解法、被证伪的假设）、**新发现**（架构新认识、工具意外行为、边界情况）。

## 阶段 2：变更分类

根据阶段 1 产出的潜在改进点，判断本轮建议将修改哪些文件类型：

- [ ] **文档变更**：项目根规范（`CLAUDE.md` / `AGENTS.md` 等）、手册库、子项目规范、个人层 memory
- [ ] **Skill 变更**：任何 `SKILL.md`（个人或项目）
- [ ] **纯代码变更或无变更**

分类结果决定阶段 5 调用哪些守门 skill。**本阶段不调用任何 audit skill**——全量审计由用户手动触发，recap 只管当轮增量。

> **如需了解现有 skill 清单或判断新建 skill**：参考项目的 skill 审计定制版中维护的 skill 清单，不要在本 skill 中维护重复清单。

## 阶段 3：改进提取

**Read `references/decision-trees.md`**，按顺序应用：

1. **改进维度分类表** → 决定条目归属哪类守门
2. **过程反哺原则** → 判断是否修 skill 而不是写 memory，以及修哪一层
3. **四问归类 + 落点矩阵 + 反例** → 每条拟落盘知识先判归属
4. **去重检查** → 写入前对照现有文件

**只提取确实有价值的改进**——不要为了输出而输出。

## 阶段 4：输出建议

按变更分类分级输出：

```markdown
## 任务回顾

### 完成的任务

[简要描述]

### 变更分类

- [ ] 文档变更（清单：...） - [ ] Skill 变更（清单：...） - [ ] 纯代码 / 无变更

> **优先级提示**：若本次执行过程暴露了所调用 skill 的方法论缺陷（subagent 漏报、步骤缺失、措辞太软），A 节首位列出该条并标注 `[过程反哺]`，优先级高于内容层更新。

### A. Skill 改进建议（新增/修订）

- **[skill 名称 / 文件路径]** — [改进类型]：当前"[原文]" → 建议"[修改后]"
- 新 skill 需求：用 skill-creator 创建

### B. 项目文档更新

- **[文档路径]** — [条目] · 归类理由：[为何项目层]

### C. 个人层 memory 更新

- **[feedback / project / user / reference]** — [条目] · 归类理由：[为何个人层]

### 无需改进

[任务顺利、无新发现时填此句]
```

## 阶段 5：确认与双守门编排执行

1. 阶段 4 的完整建议清单保留原样展示（文本形式列出所有条目，便于用户全盘审视）
2. 展示完清单后，**必须使用 `AskUserQuestion` 工具**逐条发起确认，不得让用户以文本回复的方式"全盘确认"
   - 每条建议用一个独立问题，选项固定为：采纳 / 修改后采纳 / 跳过
   - `AskUserQuestion` 每次最多 4 条问题，建议超过 4 条时分批发起
   - 条目相互独立时用单选；有明显的子项分组时可考虑 `multiSelect`（如多条 memory 追加项可合并为一个多选问题）
   - "修改后采纳"选项若被选中 → 用户会在 notes 中写出修改方向，按其修订后再次发起确认
3. 所有条目得到明确答复后，按下述编排执行：

### 5.1 双守门编排（落盘前必跑）

根据阶段 2 的变更分类调用对应定制 sync-check：

- **涉及文档变更** → 调用项目的文档落盘快检 skill（定制版 `skill-doc-sync-check-<project>`）
- **涉及 Skill 变更** → 调用项目的 skill 落盘快检 skill（定制版 `skill-sync-check-<project>`）
- **两者都涉及** → 按顺序各跑一次；任一阻断即停
- **都不涉及** → 无需守门，直接执行代码变更

守门通过 → 继续 5.2；守门阻断 → 进入 5.4 处理。

### 5.2 执行顺序

1. 项目层变更（根规范、手册库、skill 文件）
2. 个人层变更（memory）
3. 若两层有联动（例如把 memory 的条目下沉到项目规范），在同一轮内完成，避免重复条目短暂共存

### 5.3 执行工具衔接

- **修改项目根规范或其子文档** → 必须遵循项目的指南创建规则，新增独立手册需同步登记索引（具体规则由文档落盘快检 skill 守门强制）
- **修改 memory 下文件** → 调用项目的 memory 精炼 skill（如存在）统一管理
- **新增 skill** → 使用 skill-creator，不要手工创建
- **涉及代码变更**（例如 skill 中附带的示例代码） → 遵循项目的 commit 前置规则（如 simplify 等）；纯文档变更通常不触发这些规则
- **commit 消息** → 遵循项目约定

### 5.4 阻断处理（三选一）

守门阻断时暂停落盘，将阻断报告展示给用户，用户三选一：

- **A) 修正建议后重跑** → 修改阶段 4 的建议条目，重新调用守门 skill
- **B) 显式声明忽略继续** → 进入阶段 6 归档忽略项，然后继续 5.2 执行
- **C) 放弃本次落盘** → 终止流程，不做任何文件修改

### 5.5 通知与提醒

- **如果修改了 skill 文件（SKILL.md）**，用加粗和 emoji 强调提醒：**⚠️ 修改了 skill 文件，需要重启 Claude Code 才能使改动生效。**
- 用户可以选择性采纳，不必全部接受

## 阶段 6：归档忽略项

用户在 5.4 选择 B（显式忽略）时，必须将忽略项追加到项目约定的忽略项台账（通常位于 memory 目录下，由项目定制版指定具体路径）。

每条格式：

```
[YYYY-MM-DD] [doc|skill] [文件绝对路径] [问题摘要] 理由：[用户陈述]
```

- 文件不存在 → 首次创建（包含头部说明）
- 已存在 → 追加到末尾
- 该文件在下次全量审计（`skill-doc-audit` / `skill-audit` 的项目定制版）时被读取对账

## 综合考量：是否值得记录为项目资产

**见 `references/decision-trees.md` 的「综合考量」章节**（含原则、维度表、反例、判断流程）。要点：

- 涉及项目核心业务的经验，默认倾向记录
- 综合维度判断，任一强信号即可记录
- 归属判定复用四问；最终裁决：**队友 clone 应否遵守**

## 如何派生项目定制版

本 skill 是方法论版，不绑定任何具体项目的路径、skill 清单、衔接关系。**每个项目应创建自己的定制版 skill**（命名约定：`skill-recap-<project>`），内容分工如下：

| 通用 skill 负责                             | 定制 skill 负责                                                       |
| ------------------------------------------- | --------------------------------------------------------------------- |
| 六阶段流程（回顾/分类/提取/输出/守门/归档） | 本项目的 skill 清单与守门 skill 具体名称                              |
| 过程反哺原则与识别信号                      | 本项目的双守门衔接点（文档 sync-check + skill sync-check 定制版名称） |
| 四问归类原则与反例                          | 本项目的根规范/手册库/memory 目录具体路径                             |
| 综合考量维度与判断流程                      | 本项目的核心业务链路列表（给「业务核心度」做具体化）                  |
| 输出格式模板                                | 本项目的忽略项台账具体路径、commit 约定、新增手册入口                 |

**定制 skill 的开头必须声明**：

> 前置：先阅读并遵循 `skill-recap`（通用方法论）。本 skill 只列出本项目特有衔接点与路径，不重复通用内容。

如此可让通用方法论跨项目复用，各项目只维护自己的衔接部分。
