# skill-recap 决策树手册

本文件收录 `skill-recap` 在阶段 3（改进提取）与「综合考量」章节使用的决策工具：改进维度分类、四问归类、综合考量维度。主流程在遇到需要判断"这条知识归哪类"或"这件事值不值得记录"时 Read 本文件。

---

## 1. 改进维度分类表（阶段 3.1）

对识别出的改进点按下表归类，决定最终归属哪类 skill 的守门：

| 维度                                                              | 处理 skill                                                           | 示例                                           |
| ----------------------------------------------------------------- | -------------------------------------------------------------------- | ---------------------------------------------- |
| 现有 skill 的遗漏步骤 / 更优模式 / 边界陷阱 / 过时信息 / 模板缺失 | skill 变更                                                           | 「节点注册后还需检查某分类配置」               |
| 项目规范 / 架构事实 / 工程约定的新发现                            | 文档变更（项目层）                                                   | 「所有列表查询必须分页」                       |
| 个人协作偏好 / 用户纠正教训                                       | 文档变更（个人 memory）                                              | 「commit 消息用中文」                          |
| 新 skill 发现                                                     | 新增 skill，走 skill-creator                                         | 「某领域开发需独立 skill」                     |
| 本次任务的**过程**（执行流程本身）暴露了所调用 skill 的方法论盲点 | skill 变更（**先判定漂移层级：通用方法论 vs 定制拓扑 vs 项目模板**） | 具体案例沉淀到被修复的目标 skill，不在本表保留 |

---

## 2. 过程反哺原则

**如果本次任务是调用某 skill 执行的，而执行过程暴露了该 skill 自身的方法论缺陷**（漏步骤、措辞太软、subagent 没有可执行约束），**修该 skill** 比"把教训写进 memory"更有杠杆：memory 只约束我自己的下一次，skill 约束所有人的下一次。

### 修哪一层 skill 的判定（从下往上问，第一个命中即为修改目标）

1. 缺陷只与**本项目文件拓扑 / 命名 / 规则**耦合 → 修定制版 skill
2. 缺陷可复现于任何项目的同类任务（审计 / 守门 / 编排的**通用流程**有漏洞） → 修通用方法论 skill（如 `skill-doc-audit`、`skill-audit`、`skill-recap` 自身）
3. 缺陷跨多个 skill 表现为共同模式（如"subagent 都被允许用抽样代替枚举"） → 同时修被涉及的通用 skill，并考虑是否应抽取共享方法论章节

### 识别过程反哺的信号

- subagent 返回"无发现"但主 agent 亲自核对后发现漏报 → skill 对 subagent 的约束太软
- 同一类错误在不同子任务中反复出现 → skill 的强制步骤缺失
- 用户需要手动指出"应该检查 X" → skill 没把 X 写进硬性检查项
- subagent 自行降级检查强度（把"枚举"降级为"抽样"、把"差集"降级为"对照看看"） → skill 对检查强度的措辞不够刚性

遇到上述信号时，默认先改 skill 再写 memory；memory 只保留"为何此时修了这个 skill"的一句话证据。

**只提取确实有价值的改进。** 不要为了输出而输出。

## 3. 四问归类原则（阶段 3.2，写入前必做）

每条拟落盘的知识必须先判断归属，不要默认写 memory：

1. **队友 clone 仓库后也应该遵守吗？** → 是，则属于项目资产，写入项目根规范或其子文档
2. **这是用户个人对我的纠正或协作偏好吗？** → 是，则属于个人层，写入 memory (feedback)
3. **这是会过期的项目状态**（谁在做什么、重构进度）**吗？** → 是，则写入 memory (project)
4. **这条教训是因为现有 skill 的方法论缺陷才踩的坑吗？** → 是，则优先改 skill（通用版 > 定制版 > 项目 skill），写 memory 只作为补充；**不要把 skill 的缺陷用 memory 绕过去**

### 落点矩阵

| 内容类型                                    | 具体位置                                                                    |
| ------------------------------------------- | --------------------------------------------------------------------------- |
| 项目资产（四问 1 命中：架构 / 规范 / 工具共识） | 项目根规范的「规则」/「工程规范」节；子模块规范依项目的指南创建规则新建手册 |
| 个人层（四问 2/3 命中：偏好 / 纠正 / 时效状态） | memory 对应节追加；外部文件放 `memory/<topic>.md`                           |
| 方法论缺陷（四问 4 命中）                   | 修对应 skill；memory 只留"触发修复的一句话证据"                             |

### 反例

- ❌「所有列表查询必须分页」写入 memory —— 这是团队规范，应在项目根规范
- ❌「React 19 + Mantine 8」写入 memory —— 这是项目事实，应在项目根规范
- ❌「我的 commit 习惯用中文」写入项目根规范 —— 这是个人偏好，应在 memory
- ❌ 某 skill 的执行过程暴露了方法论漏洞（如 subagent 漏报、审计步骤被降级为抽样），**仅把现象写进 memory feedback** —— 正确做法：修复该 skill 的方法论本身，memory 只作为"本次触发修复的证据"而非规避缺陷的绕行记录

## 4. 去重检查（阶段 3.3，写入前必做）

写入前对照现有文件检查是否重叠：

1. 读取项目根规范与 memory 索引（通常均级联加载，已在上下文中）
2. 如拟写入条目在另一份文件已存在或等价 → 不要重复写，必要时只更新原条目
3. 如新条目使某旧条目过时 → 同步删除或标注更新旧条目

---

## 5. 综合考量：是否值得记录为项目资产

**原则**：涉及项目核心业务的经验，默认倾向记录。"只影响一处代码"不是跳过的理由——核心业务一处踩的坑往往是协议 / 框架层面的，下次别人 / 别处都会再踩。

### 维度表（**综合**判断，任一强信号即可记录）

| 维度             | 信号                                                |
| ---------------- | --------------------------------------------------- |
| **业务核心度**   | 属于项目核心业务链路                                |
| **踩坑代价**     | 定位耗时超 30 分钟 / 多人可能重踩                   |
| **非代码可见性** | 协议 / 框架隐含行为、运行时副作用、三方库未文档化边界 |
| **未来高频度**   | 正在迭代的核心模块、已知待扩展抽象                  |
| **替代来源弱**   | 需读 node_modules 源码才能确认                      |

### 反例

- 一次性脚本内部逻辑
- 唯一一处的修复且三方库 issue 有官方说明
- 纯风格偏好（走 memory）

### 判断流程

1. 命中**业务核心度** → 再看其余维度，任两项命中就记录
2. 未命中**业务核心度** → 按「回顾原则」的"值得 / 跳过"场景判断
3. 归属判定复用四问原则；最终裁决：**队友 clone 应否遵守**
