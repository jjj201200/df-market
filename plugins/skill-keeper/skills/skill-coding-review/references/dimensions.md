# skill-coding-review 三维度审查 + 等级分类手册

本 reference 详述 `skill-coding-review` 的三个审查维度与等级化分类标准。主流程步骤 2 组装 subagent prompt 时 Read 本文件的"维度定义"段；步骤 4 列决策表时 Read 本文件的"等级化分类"段。

---

## 三维度定义

**默认策略**：派发三个 subagent，每个专注一个维度（见 SKILL.md 步骤 2 工作量分档）。按工作量可压缩到 1-2 个或扩展到 > 3 个；但**不要无理由合并**——注意力分散会降低发现率。

### 维度 1. Reuse（代码复用）

**审什么**：

- 本轮新增代码是否与现有工具/helper 重复造轮子
- 同一字面量在多处硬编码（应抽常量）
- 同一行为模式在多个模块各自实现（应抽共享函数）
- 已存在的第三方库可直接使用，却手写了等价实现

**典型发现**：

- "`foo.ts:45` 的日期格式化与 `utils/date.ts:12` 的 `formatDate` 重复，应复用"
- "字符串字面量 `'application/json'` 在 5 处出现，应抽为 `CONTENT_TYPES.JSON` 常量"

**误报过滤**：

- 字面量抽常量：**真的复制粘贴 ≥ 3 处**才建议；纯风格偏好（2 处相似）不算
- 抽共享函数：两处"看起来像"但实际参数/返回语义不同 → 不抽

---

### 维度 2. Quality（代码质量）

**审什么**：

- 类型断言（`as unknown`、`as X`）是否吞掉了不该吞的错误类型
- 错误处理是否缺失 / 静默 catch / 仅 `console.log`
- 命名是否与实际行为偏离（方法名 `save` 实际是 `upsert`）
- 测试覆盖是否缺口（新增的分支逻辑无对应测试）
- 安全漏洞（SQL 拼接、XSS、命令注入、敏感信息泄露）
- 防御性编程过度（大量非必要的 `if (!x) return`）

**典型发现**：

- "`caller.ts:289` 用 `as unknown as FooDto` 吞掉了类型错误，`createBatch` 返回的 items 缺少 `description` 字段，会导致持久化时静默丢失"
- "`handler.ts:55` 的 `try/catch` 只 `console.log(err)` 没抛出，调用方无法感知失败"

**误报过滤**：

- WHAT 注释 / JSDoc / 分节注释（`// ========== xxx ==========`）：**项目 CLAUDE.md 没明说要删的就不要建议删**（这是来自通用 code-reviewer 默认模板的偏见，跨项目不一致）
- 命名偏好："`handleX` vs `onX`" 纯风格偏好，不算质量问题

---

### 维度 3. Efficiency（效率）

**审什么**：

- 重复计算（循环内做可以提到循环外的计算）
- 不必要的循环嵌套（O(n²) 可降为 O(n)）
- 可批量化的请求（for 循环内逐次 await）
- 无用的深拷贝 / 不必要的序列化
- 索引缺失（数据库查询 / Map 查找 / 集合筛选）

**典型发现**：

- "`processor.ts:78` 的 `for` 循环内 `await db.find(...)` 共 N 次，应改为 `db.findMany({ in: ids })` 一次查"
- "`render.ts:145` 每次 render 重建 `new Date().toISOString()` 可缓存"

**误报过滤**：

- 过早优化："把 `O(n)` 优化为 `O(log n)`" 但 n 永远 < 100 → 误报
- 可读性胜过微优化："把 `map/filter` 合并为单个 `reduce`" → 多数情况下是误报

## 等级化分类（三级）

每条发现项必须标注等级。禁止把 Minor 标成 Critical，也禁止把 Critical 标成 Minor。

### Critical（必修）

**定义**：软件真的不能用 / 安全漏洞 / 数据丢失风险 / 功能破坏

**示例**：

- 签名缺字段导致持久化静默丢失（见 `skill-subagent-check/references/dimensions.md` 5.1）
- SQL 拼接、XSS、命令注入
- 异步代码缺 await 导致并发竞争
- 主流程的 `try/catch` 吞掉错误不抛

**决策约束**：Critical **不允许"归档 backlog"**——必须本轮修复，或显式向用户请示并说明"为何本次不修"。

### Important（应修）

**定义**：架构问题、测试缺口、错误处理不足、明显的重复代码

**示例**：

- 同一行为 ≥ 3 处重复（可抽共享函数）
- 新增分支逻辑无对应测试
- 错误处理仅 `console.log` 未抛出
- 批量请求可优化为单次

**决策约束**：Important 可归档 backlog，但**理由必须具体**（"需要前端配合"、"独立 PR 处理"、"需要协议讨论"），不允许 "以后再说"。

### Minor（锦上添花）

**定义**：代码风格、小优化、文档完善

**示例**：

- 变量命名可以更准
- 循环可以更简洁
- 注释可以补充

**决策约束**：自由决策。默认建议"归档 backlog"而非当轮修复，避免 PR 膨胀。

## 典型误报模式（三维度共有）

subagent 容易把以下情况误判为"问题"，收到这类发现时倾向判定为"误报"：

1. **无调用点的扩展点**：方法声称"为 X 预留"但全仓 Grep 无调用 → 不是误报而是 YAGNI 死代码（**应建议删除**，不是保留）。判定为"归档 backlog"或"修"，不是误报。
2. **覆盖率 100% 的神话**：subagent 经常建议"补全所有分支的测试"——应过滤到实际风险点。
3. **风格偏好冒充质量**：箭头函数 vs 函数声明 / `async/await` vs `.then` / `const` 排序 → 误报。
4. **防御性过度**：内部函数间调用、双方都可信的参数，不需要 `if (!x) throw` → 误报（除非是边界代码）。
5. **工具提示**：subagent 建议用"`_.isEmpty(x)`" 替代 `!x || x.length === 0` —— 项目未引入 lodash 时是误报。

## 工具纪律

- 决策表填写**必须引用 subagent 报告的原文**作为等级判定证据
- 对"修 / 归档 / 误报"三分类任意决策，理由栏必须 ≥ 10 字
- 与 `skill-subagent-check` 的关系：本文件讲"怎么审"，subagent-check dimensions.md 讲"subagent 报告可不可信"——两份都读
