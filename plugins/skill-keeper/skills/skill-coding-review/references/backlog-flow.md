# Backlog 归档流程

本 reference 是 `skill-coding-review` 步骤 5（backlog 归档）的执行手册。每轮 review 结束**必跑**——不允许因"本轮没 backlog"就跳过整理。

---

## 统一到单一 backlog 文件

subagent 提出的"有价值但非本次范围"建议（性能优化、分层重构、命名优化、同类隐患等）若就地丢弃会随会话结束消失。统一写入项目 backlog 文件（默认 `memory/pending-tasks.md`，由定制版指定）。

**硬规则**：不允许新建专题 memory 文件分散归档——单一入口便于检索与提醒。

---

## 5 步整理流程（每次追加前必跑）

`backlog` 文件不是流水账，也不是只读区。**每次要追加任何条目前**，必须对整个文件执行以下整理步骤——不只是 review 分组，而是**全文扫描**。

### 步骤 1. 删除已完成项

逐条核对每个 pending / 进行中条目是否已被某次 commit、PR、用户确认放弃所解决——已解决的**整条删除**，不留"已完成 ✅"尸体。

**验证手段**：

- `git log --oneline` 查近期 commit 是否覆盖该项
- `Read` 验证目标文件是否已是建议状态
- 必要时直接询问用户

### 步骤 2. 去重合并

新条目与已有条目若描述同一件事，**合并到同一条**，"来源"字段追加新轮次；不要保留两条独立记录。

### 步骤 3. 状态推进

剩下未完成的条目，更新状态字段：

- `pending` → `待与用户确认` / `已分流到 plan-X` / `blocked` 等
- 状态描述已过期的**重写**，不要叠加旧状态

### 步骤 4. 重新分组

保持文件按主题分组（通用分组建议）：

- `进行中实施`
- `测试补充`
- `review 累积优化项`
- `架构/重构建议`
- `文档补充`
- `blocked / 待协议讨论`

不让条目按时间散落到错误分组。

### 步骤 5. 空分组清理

某分组所有条目都被删除后，**整个分组标题也删掉**——不要留空分组。

---

## 硬性顺序

**整理 → 追加新项 → 写入**。

- 没整理就追加 = 让 backlog 文件一次比一次乱、一次比一次大、最终没人愿意看
- 整理完成后再追加本轮的"归档 backlog"项（决策表中判定为"归档 backlog"的发现）
- 整理过程要有**可见的输出**（向用户简短报告"清理了 X 条已完成、合并了 Y 条重复、新增 Z 条本次累积"），不要静默改文件

---

## 单条归档格式

```markdown
- **[文件:行号] 问题简述**
  - 建议：xxx
  - 来源：YYYY-MM-DD review 第 N 轮 / agent <类型>
  - 状态：pending / 待与用户确认 / 已分流到 plan-X
```

---

## 自动流程，不征求意见

backlog 的整理 + 写入是硬规则的一部分——**不需要用户批准、不要逐项问"要不要现在处理"**。

每轮 review 结束时：

1. 自动整理 backlog（删已完成 / 合并重复 / 推进状态 / 重新分组）
2. 自动追加本轮新增的"归档 backlog"项
3. 用一段短输出告诉用户"这次清理了 X 条、合并 Y 条、新增 Z 条"——**仅汇报，不征求意见**

---

## push 完成后的总结（强制）

push（或 commit 完成后）主流程必须在结尾输出一段**简短总结**，含：

- 本次提交做了什么（一两行）
- backlog 当前未处理项清单（简短 bullets，不超 10 条）

### 模板

```
已 commit/push：<一句话描述>。

backlog 当前积压 N 项（详见 <backlog 文件绝对路径>）：

- [位置] 问题摘要
- ...（**最多 10 条**；超出用「... 等 X 条」省略，引导用户看 backlog 文件全貌）

如需处理任意一项告诉我。
```

**硬性约束**：

- **清单最多 10 条**——超出则只列前 10 条，末尾加一句「... 等 X 条详见 `<backlog 文件路径>`」。防止总结段过长淹没关键信息
- **排序**：按严重等级（Critical 优先）或按本轮 review 新增倒序，让最值得关注的先露出

定制版可补充项目 commit 约定、对 push 后总结的具体措辞做本土化调整。
