# skill-subagent-check 核查维度手册（5 维度）

本 reference 详述 `skill-subagent-check` 的 5 个核查维度。主流程执行阶段 Read 本文件，按每个维度的"判定规则 / 常见降级模式 / 证据格式 / 示例"逐项做。

---

## 1. 工具调用计数

**判定规则**：

- 核对 subagent 报告里的 `tool_uses` 或 `<usage>` 计数
- `tool_uses < 派发 prompt 要求的下限 N` → **阻断**
- `tool_uses = 0` → **无条件阻断**（直接判"空载回答"——subagent 没真做事就出结论是高发事故）

**常见降级模式（直接阻断）**：

- 报告里完全不提及工具调用次数 / 省略 `<usage>` 段
- 把"阅读了相关内容"当成"调用了工具"——实际未 Read / Grep
- 调用次数明显偏低（如要求 ≥ 5 次但只有 2 次）

**证据格式**：

- ✅ "工具调用：7 次（Read × 4、Grep × 2、Glob × 1）"
- ❌ "已充分查阅相关文件"

**示例**：

- 派发要求 N ≥ 5，报告写 "tool_uses: 3" → 阻断，走 A 选项（重派，prompt 加 "至少 5 次"）
- 派发要求 N ≥ 5，报告无 `<usage>` 段 → 阻断，走 A 选项（重派，prompt 加 "末尾必须汇报 tool_uses 数字"）

## 2. 已读清单完整性

**判定规则**：

- 报告末尾必须附"已读文件清单"
- 清单中每条必须是**绝对路径**（或明确的相对根路径前缀，如 `<repo>/src/...`）
- 清单条数 < 3 且任务并非一次性 lookup → **阻断**
- 清单缺失 → **阻断**，退回让 subagent 补

**常见降级模式（直接阻断）**：

- 仅给文件名不给路径（"parser.js"——哪个 parser.js？）
- 用相对路径但没声明根（"plugins/..."——相对哪个 repo？）
- 清单用"等"或"..."省略
- 报告声称读了 10 个文件但清单只列 2 个

**证据格式**：

- ✅ "已读：`/Users/df2025/github/df-market/plugins/token-reporter/src/parser.js:1-200`, `<repo>/CLAUDE.md:1-120`, ..."
- ❌ "已查阅 parser.js / server.js 等相关文件"

**示例**：

- 任务是"审计 3 份文档的一致性"，报告已读清单只有 2 条 → 阻断（至少 3 份都要读过）
- 清单写 "src/parser.js, src/server.js" → 阻断（无绝对路径前缀，无法验证读了哪份 repo）

## 3. 枚举 vs 抽样降级

**判定规则**：

关键检查项声称"无发现"时，必须附具体差集数字（例如 `|A|=50, |B|=48, A−B = 2 条: [x, y]`）。仅有"一致 / 无问题 / 全部通过"这类定性陈述 → **阻断**。

**常见降级模式（直接阻断）**：

- "随机抽样 3-5 条未发现问题" 替代 "全量枚举差集"
- "大致对照一遍" 替代 "逐项核对"
- "未见明显错误" 替代 "检查每一处 X 的 Y"
- "整体看起来一致" 替代 "A 集合 vs B 集合的差集"
- 报告用模糊副词兜底（"基本"、"大体"、"应该"）

**证据格式**：

- ✅ "索引条目数 |索引|=12，插件目录数 |目录|=12，差集：∅（完全一致）"
- ✅ "源字段 A = {name, version, description}（3 项），目标字段 B = {name, version}（2 项），A−B = {description}"
- ❌ "索引与目录内容大致对应，未见遗漏"
- ❌ "抽查了 3 个字段，均一致"

**示例**：

- 任务是"检查 marketplace.json 与 plugins/ 目录是否一致"，报告写"大致一致" → 阻断（必须给两个集合的势 + 差集清单）
- 任务是"核查所有 SKILL.md 的 frontmatter name 字段与目录名一致"，报告写"抽查 5 个，都对" → 阻断（要求全量枚举，不是抽样）

## 4. 结论与证据连通

**判定规则**：

每条结论必须引用**具体代码位置**（`file:line` 或 `file#section`）或**具体文件名**。仅凭模型先验给出的抽象结论 → **阻断**。

**常见降级模式（直接阻断）**：

- "根据经验" / "通常这类代码会 ..." 不带具体定位的推断
- "实现与调用对齐，未发现问题" 不指具体位置
- "遵循最佳实践" 等抽象评价
- 引用泛指文件但不给行号（"见 parser.js"）

**证据格式**：

- ✅ "`foo.service.ts:59` 的 `createBatch` 签名缺 `X` 字段，`caller.ts:289` 调用处已传但被 `map` 丢弃"
- ✅ "`CLAUDE.md#L163` 声明 5 份 skill，但 `plugins/skill-keeper/skills/` 下实际有 6 份（差集：`skill-subagent-check`）"
- ❌ "createBatch 实现与调用对齐，未发现问题"
- ❌ "文档声明与实际实现保持一致"

**示例**：

- 报告结论"本 PR 代码质量良好，未发现问题" → 阻断（无任何 file:line 支撑）
- 报告结论"已验证 A 模块与 B 模块接口对齐" → 阻断（必须附双向 file:line 引用）

## 5. 跨 agent 盲区覆盖

**判定规则**：

主调方可在输入里提供"高危维度清单"。对清单上的**每个**维度：

- 报告**必须明确表态**（"已检查 X 维度 + 结论 + 证据"）
- 跳过某维度而不声明 → **阻断**

主调方未提供清单时，按本节末尾的 4 条通用模板做兜底检查（任务涉及哪类场景则要求对应盲区被表态）。

**证据格式**：

- ✅ "已检查『签名 vs 持久层 required 字段对照』维度：`createBatch` 签名 = 持久层 required 字段（file:line 对照），差集 ∅"
- ❌ 报告里完全不提主调方点名的某维度

### 通用高危盲区模板（4 条，主调方可复用 / 增删）

- **5.1 签名 vs 持久层 required 字段对照** — 场景：批量写入 / ORM / schema 持久层 → 检查：items 接口字段 vs ORM required 字段一一对应，调用方传入但签名未列会被静默丢弃 → 典型降级："签名已覆盖主要字段"（未给差集）
- **5.2 类型断言宽泛化** — 场景：TS / Python 类型收窄、`as` 断言 → 检查：`as unknown`、`as {x?: Y}` 是否吞掉不该吞的错误类型 → 典型降级："类型断言使用合理"（未列每处断言 + 吞掉的错误类型）
- **5.3 索引硬性规则** — 场景：文档索引 / 导航目录 / 插件 registry → 检查：声称"索引与目录一致"必须给 `|A|, |B|` 数字 → 典型降级："索引已对齐"（无两集合的势）
- **5.4 YAGNI 死代码** — 场景：新增 API / 预留字段 / 扩展签名 → 检查：方法声称"为 X 预留"但无调用点应建议删除 → 典型降级："该字段为未来功能预留"（无 Grep 调用点证据）

## 工具纪律

- **只读**：禁止 Write / Edit
- **核查优先用 Read / Grep**：直接从 subagent 报告文本中取证；不需要 subagent 再跑一次
- **派发 prompt 摘要须 Read 原始**：不要凭主调方转述，读派发时的实际 prompt 文本
- **反模式**：在本 skill 运行过程中调用新的 subagent 去"验证"旧 subagent（无限递归 / 污染链）——有问题走 A/B/C 处理选项

---

## 汇总规则

- 去重：按 `(维度编号, 问题指纹)` 二元组去重
- 排序：工具调用 = 0 > 工具调用 < N > 已读清单缺失 > 差集数字缺失 > 证据定位缺失 > 盲区维度漏表态
- 输出：阻断时只列问题清单 + 三选一提示；通过时按 SKILL.md 的"通过"格式输出
- 证据要求：每条阻断问题必须附报告原文摘录（打引号），方便主调方验证判定
