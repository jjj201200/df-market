# Hook / CI 宿主文件骨架（环节 6.5 Q5 使用）

Q5 = `pre-push-hook` / `pre-commit-hook` / `ci` 时，skill-creator 按本文件的骨架 + `check-catalog.md` 的对应宿主展开，组装落盘文件。

**硬约束**：

- 骨架里的检查逻辑**不在此文件展开**——由 skill-creator 从 `check-catalog.md` 抽取
- 所有 hook / yaml 文件由 skill-creator 按 `{{projectAnswers}}` 动态生成，release-creator 插件目录不预置
- hook 文件落盘后需 `chmod +x`（由 skill-creator 处理）

---

## 1. `pre-push-hook` 骨架

落盘路径由 `{{hookLocation}}` 决定（**welcome 环节 7.6 采集**，见 `bump-check-flow.md` 第 4 节）：

| `{{hookLocation}}` | 落盘路径 | 适用场景 | 启用方式 |
| --- | --- | --- | --- |
| `.git/hooks/` | `.git/hooks/pre-push` | 单人仓库、想要零配置 | 无需额外配置——git 原生读此目录 |
| `.githooks/` | `.githooks/pre-push` | 多人协作需要版本化 hook | 需 `git config core.hooksPath .githooks`（每位 clone 者各自执行） |
| `.husky/` | `.husky/pre-push` | 项目已用 Husky / pre-commit 框架 | `npm install` 后 Husky 自动 setup |

权衡要点：

- **`.git/hooks/`** 的 hook 不会随 clone 传播——别人 clone 后拿不到你的 hook，需要自行复制
- **`.githooks/`** 可被版本化（纳入 git），但**不会自动启用**，必须 `git config core.hooksPath` 指向它；派生 SKILL.md 需要在 README 段提醒这一步
- **`.husky/`** 自动化最好但绑定 npm 生态；非 npm 项目不建议

### 默认值推导

`{{hookLocation}}` 默认值按下表（可在 welcome 环节 7.6 override）：

| 前序答案 | 默认 `{{hookLocation}}` |
| --- | --- |
| `{{ecosystem}} ∈ {npm, pnpm, yarn}` 且存在 `.husky/` 目录 | `.husky/` |
| 仓库已存在 `.githooks/` 目录 | `.githooks/` |
| 其他（含单人仓库 / 无现成 hook 目录） | `.git/hooks/` |

### 骨架内容（通用基础版）

```bash
#!/usr/bin/env bash
# Auto-generated by release-creator (derived skill: {{targetName}})
{{#if hookLocation == '.githooks/'}}# 启用方式: git config core.hooksPath .githooks{{/if}}
{{#if hookLocation == '.husky/'}}. "$(dirname -- "$0")/_/husky.sh"{{/if}}
set -euo pipefail

echo "▶ Running pre-push checks for {{packageName}}..."

# skill-creator 在此处按 Q4 多选结果依次拼入 check-catalog.md 的 [hook] 展开
{{#each selectedChecks}}
# --- {{this}} ---
{{lookupHook this}}
{{/each}}

echo "✅ All pre-push checks passed"
```

### Husky shebang 替代

`{{hookLocation}} = .husky/` 时顶部 shebang 用 `#!/usr/bin/env sh` 且紧跟 `. "$(dirname -- "$0")/_/husky.sh"`（Husky 7+ 约定）；其他两种 hookLocation 用 `#!/usr/bin/env bash`。

### 与既有 hook 共存

若目标路径（`.git/hooks/pre-push` 等）**已存在**：skill-creator 不得默默覆盖。处理策略见 `skill-creator-prompt-template.md` 的「落盘前检查」段（冲突 AUQ：覆盖 / 跳过 / 改名）。常见场景是用户仓库里本地已经写了 frontend build / lint 之类的 pre-push 逻辑——覆盖意味着丢失这些。

**合并场景的排序原则**：若用户选择 `覆盖` 并手动合并既有逻辑，应把 release check（本 skill 生成的段）放在**耗时步骤之前**——check 通常几百毫秒级，build/lint 通常秒级。早失败能省下耗时步骤的时间。skill-creator 在 AUQ 提示里附加这条建议，但不替用户做自动合并（手动合并由用户判断如何保留原有逻辑）。

## 2. `pre-commit-hook` 骨架

落盘路径与 §1 同——由 `{{hookLocation}}` 决定：

- `.git/hooks/pre-commit` / `.githooks/pre-commit` / `.husky/pre-commit`

```bash
#!/usr/bin/env bash
# Auto-generated by release-creator (derived skill: {{targetName}})
{{#if hookLocation == '.githooks/'}}# 启用方式: git config core.hooksPath .githooks{{/if}}
{{#if hookLocation == '.husky/'}}. "$(dirname -- "$0")/_/husky.sh"{{/if}}
set -euo pipefail

# 与 pre-push 相同的检查框架，但通常只包含 regex-compliance / mirror-consistency
# bump-in-diff 检查不建议放 pre-commit（此时 commit 还没成型）
{{#each selectedChecks}}
{{lookupHook this}}
{{/each}}
```

### 适用性提示

`check-catalog.md` 里的 `bump-in-diff` 检查**不适合** pre-commit 宿主（commit 尚未形成）。skill-creator 在组装 pre-commit 骨架时自动过滤掉这个检查项，并在生成过程向用户给出一行提示：

```
ℹ️ 已从 pre-commit hook 中移除 `bump-in-diff` 检查（该检查需要 commit 已存在，仅适用于 pre-push / ci）。
```

## 3. `ci` 骨架（GitHub Actions）

落盘路径 `.github/workflows/release-check.yml`：

```yaml
# Auto-generated by release-creator (derived skill: {{targetName}})
name: Release Check

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      # skill-creator 在此处按 Q4 多选结果依次拼入 check-catalog.md 的 [ci] 展开
      {{#each selectedChecks}}
      {{lookupCi this}}
      {{/each}}
```

### `{{setup-steps}}` 追加

根据生态自动追加语言 setup step：

| ecosystem        | setup step                                             |
| ---------------- | ------------------------------------------------------ |
| `npm` / `pnpm` / `yarn` | `- uses: actions/setup-node@v4\n  with:\n    node-version: '20'` |
| `python-*`       | `- uses: actions/setup-python@v5\n  with:\n    python-version: '3.12'` |
| `claude-plugin`  | `- uses: actions/setup-node@v4`（脚本用 node）          |
| `docs-only`      | 无需 setup                                             |

skill-creator 在 `steps:` 段的 checkout 之后、check 展开之前，插入对应 setup。

## 4. 非 GitHub 平台（其他 CI）

Q5 选「ci」时，若生态维度记录的仓库**不是** GitHub（例如 GitLab / Gitea），skill-creator:

- 默认仍生成 `.github/workflows/release-check.yml` + 在派生 SKILL.md 顶部加 `TODO: 请将 GitHub Actions 语法翻译为你的 CI 平台（<platform>）` 提示
- 或提示用户改选 `pre-push-hook`（本地检查，平台无关）
- **不**自动生成 `.gitlab-ci.yml` / `Jenkinsfile`（避免在不确定平台上假设太多）

## 5. check 脚本（供 hook 调用）

Q5 选 hook 时，skill-creator **除了**落 hook 文件，还要落一份 `{{scriptsDir}}/check-version.<ext>` —— 包含 `check-catalog.md` 所选项的 **bash 展开**，hook 文件只是个薄包装：

```bash
# {{hookLocation}}pre-push 的实际内容（示例：hookLocation=.git/hooks/、scriptsDir=scripts/）
#!/usr/bin/env bash
exec bash "$(git rev-parse --show-toplevel)/scripts/check-version.sh" "$@"
```

这样 release skill 里也能直接手动跑 `bash scripts/check-version.sh` 验证，与 hook 自动触发对称。

`check-version.<ext>` 内容按 `check-catalog.md` bash 展开拼接，脚本顶部统一加：

```bash
#!/usr/bin/env bash
# Auto-generated by release-creator (derived skill: {{targetName}})
set -euo pipefail

# --- 各 check 项按 Q4 顺序依次展开 ---
```

## 组装规则（skill-creator 调用）

1. 读 `{{projectAnswers}}.checkTiming`（Q5 单选）+ `.checkScope`（Q4 多选）+ `.hookLocation`（Q5 hook 子问，仅 hook 时机需要）
2. 按 timing 选骨架（本文件对应章节）
3. 把 `selectedChecks` 按序从 `check-catalog.md` 抽对应宿主展开填入占位
4. 若 timing = hook，除 hook 文件外**同时**落 `check-version.<ext>`（位置由 `{{scriptsDir}}` 决定，hook 位置由 `{{hookLocation}}` 决定——**两者独立**）
5. Hook 文件落盘后 `chmod +x`
6. 在派生 SKILL.md 顶部按 `{{hookLocation}}` 条件说明「启用方式」：
   - `.git/hooks/` → 无需启用（注明"hook 不会随 clone 传播，协作者需手动复制"）
   - `.githooks/` → `git config core.hooksPath .githooks`
   - `.husky/` → `npm install`（Husky 自动 setup）
